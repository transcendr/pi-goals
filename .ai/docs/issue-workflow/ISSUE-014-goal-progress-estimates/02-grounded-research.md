# 02 — Grounded research

Issue: ISSUE-014 — agent-estimated goal progress percentage
Date: 2026-05-10

## Existing refine issue state

Source: `.ai/issues/refine/ISSUE-014-goal-progress-estimates.md`

The refine issue already defines the user-visible goal: optional agent-updated progress estimates such as `35%` with an optional rationale. It explicitly says the estimate is subjective and must not be confused with completion proof.

It was not execution-ready because it left these forks open:

- whether progress belongs on `GoalState`, telemetry, or a separate event stream;
- numeric range semantics;
- whether notes are required;
- stale/age display behavior;
- narrow widget rendering;
- whether progress updates count as work for no-progress safety counters.

## Current runtime state model

Sources:

- `.pi/extensions/goal/types.ts`
- `.pi/extensions/goal/state.ts`
- `.pi/extensions/goal/tools.ts`
- `.pi/extensions/goal/tool-results.ts`

Findings:

- `GoalState` currently stores user-visible durable goal facts: objective, status, budgets, floors, usage, `createdAt`, and `updatedAt`.
- `GoalTelemetrySnapshot` stores internal runtime/safety facts: turn counts, skip reasons, safety pause reason, budget warning flags, floor quality state, and `lastProgressAt` for no-progress accounting.
- `state.ts` persists branch-local custom events with `pi.appendEntry(STATE_ENTRY_TYPE, event)` and replays them into runtime state.
- `update_goal` already persists full `GoalState` updates and calls `syncGoalUi(ctx, update.goal)`, so state-backed progress can update UI reactively without a second persistence stream.
- `get_goal` and `update_goal` results expose `details.goal`, so progress fields on `GoalState` would be visible to agents without a bespoke output channel.

## Current update surface

Sources:

- `.pi/extensions/goal/tools.ts`
- `.pi/extensions/goal/lifecycle.ts`

Findings:

- `UpdateGoalParams` currently accepts `status`, `objective`, budgets, and floor fields; it has no progress estimate parameters.
- `buildGoalUpdate()` rejects no-op updates with `No goal updates were provided.`
- `update_goal(status: "complete")` is routed through `decideGoalCompletion()` and completion-floor checks.
- `lifecycle.ts` currently treats any successful `update_goal` result with a `goal` object as `progressCount++`. If ISSUE-014 adds progress-only updates without changing this, an agent could avoid no-progress safety pauses by repeatedly changing estimates.

## Current UI surface

Sources:

- `.pi/extensions/goal/format.ts`
- `.pi/extensions/goal/widget.ts`
- `.pi/extensions/goal/ui.ts`
- `.ai/issues/open/ISSUE-011-goal-widget-real-component-and-narrow-width.md`

Findings:

- `syncGoalUi()` refreshes both footer status and the above-editor widget after goal changes.
- Footer text is generated by `footerStatusText(goal)`.
- Summary output is generated by `goalSummaryLines(goal)` and `formatToolGoal(goal)`.
- Widget rendering is pure through `renderGoalWidget(goal, theme, width)`.
- ISSUE-011 now locks widget rules: framed mode at width `>= 32`, compact unframed below 32, no generic Card component assumption, and visible-width-safe output.
- Current `widget.ts` contains a budget `progressBar()` helper, but there are no progress estimate fields/rendering (`progressPercent`, `progressNote`, `progressUpdatedAt`). The first validation probe intentionally caught this naming ambiguity.

## Current completion/safety semantics

Sources:

- `.pi/extensions/goal/completion-gate.ts`
- `.pi/extensions/goal/telemetry.ts`
- `.pi/extensions/goal/lifecycle.ts`

Findings:

- Completion status is gated through `decideGoalCompletion()` and floor evaluation.
- Telemetry `lastProgressAt` is internal no-progress accounting, not a user-facing percentage estimate.
- `applyTurnTelemetry()` decides no-progress counters from a boolean `madeProgress` passed by lifecycle.
- A progress estimate must not set `completedGoal`, bypass completion floors, or mark a turn as productive by itself.

## Documentation state

Source: `README.md`

Findings:

- README currently says `/goal` shows “status, budgets, and progress metadata,” but current runtime does not expose user-facing progress estimates yet. ISSUE-014 should either make that true or clarify wording during implementation.

## Research conclusion

The lowest-risk first implementation is to make progress estimates an optional durable property of `GoalState`, updated through `update_goal`, rendered by existing UI helpers only when set, and ignored for completion/no-progress safety unless paired with a substantive non-progress update.
